## どのファイルに書くか

- **その 1 スタイルの見た目・形・シェーダの話** → `AETHER.md` / `VITA.md` / `VOLUME.md`
- **帯域解析・リズムイベント・蓄積・完成時の焼き込みなど、どのスタイルで描いても同じように効く層** → `COMMON.md`
- 迷ったら `COMMON.md`。スタイル固有だと分かった時点で移す。
- `COMMON.md` の項目に着手するときは、**どちらのスタイルで検証するか**を先に決める。
  片方だけ見て「直った」と報告しない。

## 運用

- 優先度 `P1`（高）→ `P2` → `P3`（低）。無いときは **簡単なものから**。
- ユーザーが **OK** と言った項目は **削除**する（打ち消し線で残さない）。
- 1 項目 = 1 まとまり。必要なら `notes` で補足。
- **`ease` はエージェントが判断する**（ユーザーが書く必要はない）。着手後に難しかったら `medium` / `hard` へ上げてよい。
- **`寄与` もエージェントが判断する**。原則の3本柱（`リアルタイム` / `蓄積` / `完成形`）のどれに効く項目かを書く。どれにも効かない項目は優先しない。
- チャットで進めるときは **「ワークリスト進めて」** でよい（対象スタイルを添えると速い）。

### フォーマット例（コピー用）

ユーザーはタイトルと notes（任意）だけでよい。`ease` と `寄与` はエージェントが追記・更新する。

```markdown
### [P2] 短いタイトル
- status: todo
- ease: easy      # エージェント記入。後から変更可
- 寄与: 完成形     # エージェント記入。リアルタイム / 蓄積 / 完成形
- notes:
```

## 優先順位の基準（原則より）

目的は「一曲を聴いた結果として、その曲だけの唯一の立体作品が生成されること」。
3本柱（**リアルタイム / 蓄積 / 完成形**）は**すべて同格に重要**。

- リアルタイムを「もう出ているから後回し」にしてはいけない
  （原則 mdc「リアルタイム性の重要度」参照。ユーザーは曲を彫刻していく**過程**にも面白みを感じる）。
- 「完成形・蓄積を先に」は**難易度が同程度のときのタイブレーク**であって、
  リアルタイムを軽視してよいという意味ではない。
- 現状の実装上の主ギャップは **蓄積**。ただし 2026-08-10 に定義を変えた（下記）。

---

## 蓄積の定義（2026-08-10 にユーザーインタビューで変更）

**以前の定義は破棄した。**「曲の展開や構成が読み取れること」は要求ではない。

| | 旧（破棄） | 新 |
|---|---|---|
| 目標 | 曲の進行・構成が読み取れる | **曲ごとの個性がシルエットに出る** |
| 手段 | 時間を空間の位置へ写す（地層） | 曲全体の特徴を最終シルエットへ収束させる |
| 進行の読み取り | 必須 | **不要** |

- 個性の源は4つとも: **曲調の激しさ / テンポ・リズムの種類 / 音色・楽器編成 /
  明るさ・音域バランス**
- 出力先は**シルエットのみ**。表面の質感・動きに曲ごとの差を担わせない。
  色も個性の主役ではないが、**天気・時間による色変化は消してはいけない**。
- 似た曲調どうしは似ていてよい。無理に散らさない。
- 「一曲を最後まで聴いた結果である」ことは必要。これが「曲としての蓄積」。

**時間 → 位置の写像（地層）は再試行しない。** ユーザー評価は「そもそも面白くなかった」で、
振幅不足ではなく方向が違っていた。

詳細と根拠は [../handoff/COMMON.md](../handoff/COMMON.md)、
原則は [project-principles.mdc](../../.cursor/rules/project-principles.mdc)。

## 蓄積を扱うときに必ず踏まえること（2026-08-06 の調査）

コードを実地調査して見つかった構造的な欠落。**新しい定義でも生き残る**（理由が変わる）。

- 蓄積の実体（accumulated / vectorField / sculptureMemory）は確かに加算式で貯まる。
- しかし accumulateWithMemory に上下限クランプがあるので、**長い曲ほど飽和し、
  どの曲も似たブロブへ収束する。** → これは新しい本命要求
  「曲ごとの個性がシルエットに出る」に真正面から反する。**最大の障害。**
- 「どこに貯まるか」を決める空間パターンは `audioSalt`
  （= spectralPhase * 1.7 + carvingPhase * 0.9 + …, main.ts）に依存し、
  この位相は曲が進むほど単調に増え続けるため、**パターン自体がスクロールする**。
  時間対応が付かないこと自体はもう問題ではないが、
  **曲の特徴がシルエットに固定されず塗り替わる**点は障害として残る。

過去に何度も試した係数調整が効かなかったのは、これらが理由。
**蓄積を扱うときは必ずここを踏まえること。**
