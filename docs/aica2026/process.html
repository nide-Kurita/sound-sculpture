Sound Sculpture

音の彫刻

音楽を「形」としてみたい。
波形を眺めるアナライザーではなく、一曲を聴き終えたあとに、その曲だけの立体が手元に残る作品です。

制作：栗田 慎之介（個人）
形態：ブラウザ上のインタラクティブ 3D 作品（Vite / TypeScript / Three.js / Web Audio）
資料作成日：2026-09-07
本資料はリポジトリ内の原則・戦略・引き継ぎメモに基づく総括です。

体験の流れ（鑑賞者）

推奨環境は Google Chrome（最新版）です。
Safari と Firefox は PC・タブ音声の取り込みに対応していないため、これらのブラウザではマイク入力のみ利用できます。

  1. ブラウザで作品を開きます。
  2. 操作パネルで Use Input Device（マイク）または Use System Audio（PC・タブ音声）を選びます。
  3. Start Recording を押すと、形成が始まります。
    画面のドラッグで回転します。
  4. 再生中は、打点・声・遊泳などに反応しながら形が育ちます。
  5. 設定パネルで、スタイル・成長アルゴリズム・時刻・天気の条件・表示言語を選べます。
  6. 無音が続くと自動で、または Complete で完成します。
    Export GLTF で書き出し、Reset でやり直せます。

1. コンセプト — なぜ作ったか

出発点は、音楽をオブジェクトとして見たいという思いです。
「この曲はどんな形になるんだろう」「この音はどんな形だろう」。
一曲を聴き終えたとき、その曲を聴いたという時間が、ひとつの目に見えるアートになっていたら面白い。
そんなところから始まりました。

音楽そのものは、多くの人が共有できるものです。
一方で、LIVE で感じるその場の空気や情緒、そのときに感じたことなど、音楽を聴いた体験は、人の記憶や心に残るものでもあります。
そうして記憶や心に残ったものが、もしひとつの物体になって目の前に現れたら、どんなものになるのか。
それを実際に見てみたいという気持ちが、この作品を作る原動力になりました。
音楽が流れているあいだだけ変化するオーディオビジュアライザーではなく、曲を最後まで聴くという行為そのものが形として刻まれ、あとから何度でも眺められるもの。
それがこのプロジェクトの芯です。

したがって本作品は、「音を分析して見せる装置」ではありません。
演奏を彫刻行為、音を物質への圧力、時間を形成プロセスとして扱い、音による変形を一時的な演出で終わらせず、形へ不可逆に蓄積します。
無音、または手動での完了によって、「その曲の痕跡」として固定します。

聴かせているあいだ、形は音に反応して変わり続けます。
気候と時刻によって素材が変化し、質感や素材感は環境と曲調に左右されます。
そして音が終わると、その時点の形が彫刻作品として出来上がります。

2. 2026年における位置づけ

2.1 音楽を「解析対象」から「見たいオブジェクト」へ

技術的には Web Audio による解析を使いますが、目的は分析結果の提示ではありません。
人が聴いている出来事（キック、スネア、ハット、主旋律の句など）を視覚の動詞へ割り当て、曲ごとの個性をシルエットと痕跡に残します。
vita スタイルでは低音寄り→粘土、中音→膜、高音→粒子という役割分担を持ちつつ、スタイルごとに読み取りやすい要素へ再割り当てできる構造を保っています。

音をそのまま形へ変換しているのではありません。
音の出来事が立体を変化させ、その変化が積み重なることで、曲ごとのシルエットが生まれます。
そのため、テンポやリズム、音色、音の密度の違いが、形の違いとして少しずつ現れます。
同じ曲を聴かせれば同じ形になること。ここは特に重視しています。
再現しないのであれば、出来上がった立体は「その曲を聴いた記録」になりません。
音源ファイルを読み込む経路では、解析を決定論的に行い、ファイルのバイト列から造形のシードを一対一で決めています。
マイクやタブ音声からのライブ入力は入力環境の影響を受けますが、同じ曲を二度聴かせたときの輪郭のずれは、別の曲どうしのずれよりはるかに小さく収まります。
逆に、別の曲を聴かせれば自然に別の形になります。
曲ごとの違いを表面の模様や色だけで表すのではなく、遠くから見て分かるシルエットそのものに現れるようにすることを目指しています。

2.2 複数スタイルの共存

公開スタイルは vita（生命）／monolith（彫刻）／dither（網点）の三つです。
どれか一つに絞って他を捨てる前提ではなく、同じ曲を違うスタイルで見られること自体を、作品の価値としています。

2.3 形の育ち方 — 13 種類の成長アルゴリズム

スタイルが「どう見えるか」を決めるのに対し、成長アルゴリズムは「どう育つか」を決めます。
音が「いつ、どれだけ」形を変化させるかを決め、成長アルゴリズムが「その変化を形のどこへ、どう広げるか」を決めます。
そのため、同じ曲でもアルゴリズムを変えれば別の形になり、同じアルゴリズムでも曲が違えば別の形になります。
フィボナッチ、葉序、反応拡散、拡散限定凝集、粘菌網、結晶成長、風化侵食など、自然界にある造形の法則をひとつずつ実装したものです。
設定パネル、または URL の ?algo= で切り替えます（既定は Fibonacci）。

アルゴリズム何の法則か
Fibonacciフィボナッチ比率による均衡した起伏
Phyllotaxis黄金角螺旋。花・松ぼっくりの葉序
L-System枝分かれ。触手・骨格・器官
Differential Growth面の押し合い。レタス・脳・珊瑚
Reaction Diffusion反応拡散。皮膚模様・侵食文様
Voronoi Growth細胞分裂・細胞の斑模様
DLA拡散限定凝集。雪の結晶・菌糸
Physarum粘菌網。神経・血管の経路
Flow Field流れ場に沿った成長
Curl Noise渦のある柔らかい有機変形
Space Colonization空間探索。木・血管・触手
Crystal Growth結晶面。鉱石・人工物の鋭さ
Erosion風化侵食。音の化石

各アルゴリズムは、頂点ごとの起伏（pattern）、流れの向き（flow）、打点や粒子の着地点（placeOnSphere）、棘の出やすさ（spikeMask）の四つを持ちます。
さらに、完成シルエットの原型（紡錘・環・柱・珊瑚・鼓）への寄り方も切り替わります。
見た目の装飾ではなく、造形の骨格を担う層です。

2.4 人と AI の共創としての制作過程

実装・調整・検証は、Cursor と Claude Code 上の AI エージェントと作者が、同じリポジトリを正本として進めました。
会話履歴に知識を残さず、原則ファイル・スタイル別ワークリスト・引き継ぎメモに、状態と失敗を書き残す運用にしています。
仮説→実装→計測（打点比・シルエット差など）→実機判定→失敗の記録という短いサイクルを繰り返している点を、AI 時代の制作モデルとしても提出します。

4. 制作の流れ（2026年夏〜）

4.1 原則の固定

「蓄積＝時系列を空間へ写すこと」ではなく、「曲全体の特徴を最終シルエットへ収束させること」と定義し直しました。
時間→位置の写像（地層）は、実装して試したうえで面白くないと判断し、却下しています。
球の半径揺らしだけでは形の種類が増えないことも、原則に明記しました。

4.2 共通エンジン（飽和の解消）

密な曲で LIVE が見えない問題を計測し、帯域ゲートの飽和、同時多発の和、自己フィードバックなどを修正しました。
打点直後の動き÷平常の動き（打点比）を、ガード指標にしています。

4.3 vita 戦略（段A→B→C）

段目的結果（要約）
A0反応語彙の診断検出欠落と表示欠落を切り分け
A1歌モノで声が見える句の寿命つき表現へ収束。ユーザー OK
A2反応の種類ハット純化を採用。キック収縮は撤回。種類差は一部未達
A3遊泳の地体スケール進行波。旧うねりと差別化。ユーザー OK
B膜＝水→結晶／粘液水・粘液 OK。結晶の読みやすさは通しで再課題化
C色の語彙天気の意味と澄さ。ユーザー OK

4.4 通し実機（2026-09-04）

段A全体の完了条件である「数分通しで飽きない」は、未達です（同じような反応で飽きる／形にこの先の驚きがない）。
一方で、打点の可読性・遊泳の地・曲の軌跡としての痕跡は肯定されました。
現状を維持したまま課題をワークリストへ残し、公開作業へ移行しています。

5.2 AI ならではの進め方（どう変わっていったか）

立ち上がり。
環境構築からモック制作までが、ものの数分で終わりました。
そのおかげで、制作の進め方や具体的な方針を早い段階で選べました。

分業の想定が外れた。
当初は、HTML や軽微な調整は人の手で対応するつもりでした。
ただ、AI が生成する HTML と CSS にルールを初期に設定していなかったため、思うように直せませんでした。
結果として、軽微な調整やデザイン面の課題も AI に指示することになり、分業したかった部分が想定とは異なる進め方になりました。
レイアウトについては、参考にしたい配置の画像を読み込ませることで、結果的に簡単に狙った形へ寄せられました。

微調整を、言葉から数値へ。
モックから具体的な調整指示を重ねるうちに、微調整を言葉で伝えることが難しくなりました。
そこで、数値をリアルタイムに動かせるコントロールパネルを画面に追加し、調整結果を JSON として書き出す方式へ変えました。
人がその場で見ながら値を決め、書き出した JSON を AI に渡して修正を確定させる。
この流れが、以降の調整の主軸になりました。
調整したい項目はまずコントロールパネルに追加してもらい、そこで人が微調整し、JSON を AI へ渡す。
この分担は、調整の方針としてはっきり良い結果になりました。

指示の出し方を、ルールと優先度へ。
最初は都度お願いする形でしたが、前提を忘れたり、更新してほしくない箇所まで調整し始めたりするようになりました。
そこで、前提ルールと調整リストを別ファイルとして制定しました。
前提ルールに沿って優先度の順に指示していく形にしたところ、手戻りが減り、意思疎通も良くなりました。
前提ルールを確認し、現状の課題を伝え、プランを立て、難易度と作業優先度を考慮した順番を付け、調整し、人が実機で確認する。問題があれば課題として提示し、プランとリストを更新する。
この循環が、AI の作業方針として良いものでした。

複数モデルの並行と、申し送り。
途中で別のモデルの AI を加えたところ、作業の競合が起きました。
そのため、モデルを分けても競合しないよう、作業ごとに申し送りを書き残させるようにしました。
これによってモデル別に作業を分けられるようになり、副次的な効果として、作業を中断して別の作業に移り、また戻ってくることも容易になりました。

この経緯の結果が、いまリポジトリに残っている次の形です。

5.3 良かった点

失敗が資産として残ったことです。
効かなかった手段を理由とセットで書き残す運用は、人の記憶に頼ると続きません。
AI が毎回書くので続き、同じ失敗を二度踏むことが減りました。
見た目の判断を数値と比較画像へ落とす習慣も、同じ理由で定着しています。

5.4 課題点

AI は、見た目を判断できません。
数値が改善すると「直った」と報告してきますが、実機で見ると直っていないことが何度もありました。
そのため、数値の合格では完了とせず、作者が実機で見て OK を出すことを必ずゲートにしています。

もうひとつは、誤った原因を、自信をもって提示してくることです。
段A1（歌声を形に出す）では、担い手を 3 回作り直して、3 回とも実機で不合格になりました。
1 巡目・2 巡目に示された「真因」はどちらも誤診で、本当の原因が分かったのは 3 巡目です。
駆動信号が時間の 95〜97% 出っぱなしで、句の切れ目が形に出ていませんでした。
この 1 点で、3 巡すべての失敗が説明できます。

そこから、「見えないと言われたら、振幅や担い手を変える前に、まず信号が出ている時間（duty）を測る」という作法をルール側へ足しました。
係数の当てずっぽうで差を出そうとする提案が繰り返し出てくることも、禁止事項として原則に明記してあります。

AI が実装と計測と記録を担い、作者が鑑賞判断・優先順位・「何が作品か」という北を握る。
この分担が、本プロジェクトにおける AI × クリエイティブの実践です。

6. 残課題（意図的に残しているもの）

6.1 作品の残課題

  • LIVE 通しでの飽き／形への驚きの不足（最大の未達）
  • 打点ごとの反応の種類差
  • 膜の状態変化の読みやすさ
  • 完成形の造形語彙の拡張（中長期）

未達を隠さず課題として残すこと自体も、制作過程の誠実さとして資料に含めています。

6.2 AI との進め方の課題

最大の未達である「飽き／驚きの不足」は、AI との進め方の課題でもあります。
いまあるものを改善する方向であれば、AI は速く、案の数も出してくれます。
ただ、想像の範疇を超える方向の案は、そのままでは出てきません。
過去の延長でうまくいきそうなものが優先されるためです。
何が面白いかを決めるのは人の側であり、そこを手放すと、破綻はしないけれど驚きもないものへ収束していきます。
この見極めを、もっと早い段階でできるようにすることが次の課題です。

二つめは、ルールを決める時期です。
最初にルールを敷かなかった領域は、後から取り返しがつきませんでした（5.2 の HTML / CSS）。
どこを人が触り、どこを AI に任せるのか。その線引きは、作り始める前に決めておくべきものでした。

三つめは、判断の往復にかかる時間です。
AI は見た目を判断できないため、最終的な合否は必ず人が実機で見て決めます。
ここは今後も変えませんが、人が見る回数を減らさずに、一度に見比べられる量を増やす。
道具の側でそこを工夫していきます。
