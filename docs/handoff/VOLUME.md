## 1. 目的・ゴール

`?style=volume` は **2026-08-10 に「別スタイルとして仕上げる」とユーザーが決めた**もの。
それまでは vita の比較用として Parked されていた。

**仕上げる理由**（ここを忘れると元の袋小路へ戻る）:

vita は `IcosahedronGeometry` の頂点を法線方向へ動かしているだけで、
**位相が常に球のまま＝穴も枝も原理的に作れない。**
ユーザーは4曲の完成形を見て「トゲトゲしているだけの違いしかない」
「2曲続けて生成した人は3曲目を作らない」と評価した。
実測でも vita の輪郭の複雑度（周囲長/√面積。円で約3.54）は 4.26〜5.08 に収まる。

volume は密度場へ音を堆積させて MarchingCubes で等値面を取るので、
**穴が開く・枝が分かれる・空洞ができる・位相が変わる。**
同じ4曲で複雑度 4.31〜10.56（幅は vita の 7.6 倍）、貫通穴も最大5個出る。

**vita は現状のまま残す。** 原則の「複数スタイルの共存が作品の価値」に沿う。
volume は vita の置き換えではない。

## 2. いまの状態

- `?style=volume` は DEV 限定（`visual-style.ts` の `PUBLIC_EXPERIENCE_IDS` に未追加）。
- 描画は `MeshPhysicalMaterial` 1枚の等値面のみ。**膜も粒子も無い。**
  vita のような「見た目の作り込み」はまだ入っていない。
- **天気・時刻・音楽性による色変化を 2026-08-10 に実装した**（下記3章）。
  それまでは `applyWeatherClayTint` / `evolveSongColors` が空実装で、
  **原則で必須の要素がまるごと欠けていた。**
- 完成時に密度場を 48³ → 72³ へ載せ替えて焼き込む。完成後は再ポリゴン化しない。
  **ここにあった `mc.blur(0.6)` は 2026-08-11 に外した**（輪郭の複雑度を最大6割削っていた。3章）。
- dev パネル（ブルーム以外）は volume でも出る。検証用キャプチャも使える。

### 2026-08-11 彫り込み・枝分かれの瞬間に閃光を出した（「動きが伝わらない」への対処）

ユーザーが選んだのは「まず光らせ、効かなければ再配分」。**まず光らせるほうを実装した。**
形（密度場）には一切触っていないので、過去2回の失敗（大きさを伸ばして複雑度を壊す）を踏まない。

実装は `src/volume-sculpture.ts` のみ。加算合成の `THREE.Points`（28スロット）を
`group` に足し、彫り込み（`carveCooldown` が切れて実際に削ったとき）と
枝分かれ（`energySurge`）で1つずつ出す。寿命 0.55 秒、深度判定は切ってある
（等値面の内側で起きた彫り込みも見せるため。一瞬なので火花として読める）。
**完成後は出さない**（作品になったら静かになる）。

トポロジーが実際に変わった瞬間を毎フレーム判定するのは高いので、
**彫り込みイベントそのものを合図にしている。** 目的は「ここが削られた」を見せることなので足りる。

実測（`flash_check.js`。60秒以降を 0.25 秒間隔で24コマ連射）:
**24コマ中5コマで閃光が出た**（白飛び画素 165〜879）。console error 0件。
画像: `docs/volume-progress/carve-flash.png`。

**ユーザーの実機確認待ち。** 見てほしいのは「後半も何か起きていると感じるか」と
「光が邪魔になっていないか」。効かなければ質量の再配分へ進む（8章）。

### 2026-08-11 天気・時刻を**彩度・明度**で伝えるようにした（ユーザーが選んだ方向）

色相では伝わらないと確定した（下記）ので、volume 専用の彩度・明度の表を持たせた。
変更したのは `src/volume-sculpture.ts` のみ。色相は共通関数のものをそのまま使い、
**彩度・明度だけ差し替える**（`VOLUME_ENV_TONE` / `volumeWeatherTone` / `volumeHourTone`）。

方針: 雨・嵐は暗く、雪・霧は白く明るく、快晴は明るく鮮やかに、雷雨は暗く鮮やかに。
時刻は深夜・夜を暗く彩度低めに、昼を明るく、夕を彩度高めに。
共通側（vita の確定値）は触っていない。

実測（完成後、`env_color_grid.js` + `png_hue.js`）:

| | 現状 | 新案 |
|---|---|---|
| 天気による彩度の幅 | 0.21 | **0.41** |
| 天気による明度の幅 | 0.052 | 0.077 |
| 時刻による彩度の幅 | 0.30 | **0.39** |

比較画像: `docs/volume-progress/env-tone-weather.png` / `env-tone-hour.png`。
現状は「快晴・曇 = ピーチ / 雨・雪・雷雨 = クリーム」の2群だったのが、
新案では快晴の鮮やかなサーモンから雪のほぼ白まで連続的に分かれる。

`npx tsc --noEmit` / `npm run build` 通過、console error 0件。**ユーザーの実機確認待ち。**
（色が前に出過ぎていないかは主観判断なので、画像と実機で見てもらう。）

**形成中の色はまだ測っていない。** 彩度・明度は `updateMaterialLive` にも効くが、
数で確かめたのは待機と完成後だけ。

### 2026-08-11 **測定の落とし穴: 完成後の色は 2.5 秒では 6 割しか到達しない**

これで一度、測定を丸ごと誤診した。**「彩度・明度も効かない」と結論しかけた。**

完成後の色は `updateAfterlife` の `material.color.lerp(..., dt * 0.9)` で追従するが、
`update()` が `dt` を 0.05 に制限しているので **1フレームあたり最大 4.5% しか進まない。**
swiftshader は 10fps 前後なので、2.5 秒待っても 6 割しか到達していない。

切り分け方: `envShiftFor` が返す値を無条件に極端な値（`sat: -1, light: -0.6`）へ差し替えて
撮ったら明度 0.78 → 0.35 と大きく動いた。つまり経路は生きていた。
次に条件名と tone 値を `console.error` で出して、値も正しく届いていることを確認した。
残るのは待ち時間だけだった。`env_color_grid.js` の待ちを 10 秒へ延ばして解決。

**教訓: volume の完成後で色を測るときは 10 秒待つ。** 縮めたら結論も疑うこと。

### 2026-08-11 色が弱い原因は**振幅ではなく、完成体が淡すぎること**。倍率も基準修正も効かなかった

上の「どちらも弱い」を受けて2通り試し、**2通りとも現状より悪化した**（詳細は5章）。
分かったことだけ書く。

**測り直したベースライン**（`weather_color_check.js`、待機、本体画素のみ）:
天気 0.040 / 時刻 0.019。ユーザーの体感（天気はなんとなく／時刻は全く）と一致する。
**時刻が弱いのは元の時刻カーブの色相幅が ±0.045 しか無いため。**

**完成後は待機と別の経路を通る。** 形成中は `updateMaterialLive` が色相へ直接足すが、
完成後は `applyEnvShiftToSculpturePalette` を通り、**色相が [0.02, 0.92] にクランプされる。**
volume の完成パレットは色相 0.06〜0.14 の暖色なのに、ずらしは基準色相 0.6 に対して
計算されていて大半が負方向なので、下限に張り付く。
そのため **倍率を上げると天気の差はむしろ縮む**（完成後の色相幅 1倍 0.081 → 5倍 0.064）。

**しかし基準を直しても見た目は良くならなかった。** 完成体は明度 0.78 と淡く、
この明度では色相を動かしても色として読めない。倍率を上げると白へ抜けるだけだった。
比較画像 `docs/volume-progress/env-weather-gain.png`（現状 / 弱 / 中 / 強の4行 × 天気5種）。
時刻のほうは `docs/volume-progress/env-hour-gain.png`（倍率 1 / 2.5 / 5.5 の3行 × 4時刻）で、
**3行がほぼ見分けられない**。完成後に時刻で色が動いて見えるぶんは、
ずらしではなく**照明**が作っている。
**現状が一番判別できる**（快晴・曇 = ピーチ / 雨・雪・雷雨 = クリームの2群）。
皮肉だが、クランプで色相 0.02 に張り付くことが強いピーチを作っていた。

コードは現状の実装へ戻してある（`npx tsc --noEmit` / `npm run build` 通過）。
`envShiftFor` に却下理由をコメントで残した。

**次に取るべき方向**（ユーザー判断待ち。8章）: 色相ではなく
**明度・彩度で天気を伝える**（雨は暗く青く、快晴は明るく暖かく、雪は白く）。
淡い完成体の上で読めるのはこちら。ただし完成品の見た目が今より大きく動くので合意が要る。

### 2026-08-11 完成時の `mc.blur(0.6)` を外した。**輪郭の複雑度を最大6割削っていた**

「演奏中は複雑な形をしているのに、完成した瞬間に単純になる」の主因。
コードには「わずかに均して、堆積の階段状のむらを取る（形の骨格は残る）」と
書かれていたが、**骨格は残っていなかった。**

切り分け方（`complete_ab.js`。**1回2分**）: 曲を60秒だけ聴かせて Complete を押し、
**完成前後を同じ個体で撮って比べる**。曲を最後まで通すと1回4〜7分かかるうえ、
run ごとのばらつきに埋もれる（下記の注意）。

| | blur 0.6 | blur なし |
|---|---|---|
| I'm Yours（形成中 → 完成） | 11.99 → 4.87（**0.41倍**） | 10.41 → 11.33（1.09倍） |
| Fury（形成中 → 完成） | 11.28 → 8.20（0.73倍） | 12.13 → 10.54（0.87倍） |

**2曲とも、ぼかしを外したほうが完成時の複雑度が保たれる。** 値を 0.25 に下げても
I'm Yours は 12.65 → 6.20（0.49倍）と半減したので、段階調整では解決しない。

外して出るはずだった「階段状のむら」は、72³ への載せ替えと MarchingCubes の法線で
十分滑らかになっており、画像で確認しても粗は出ていない。

**破片の除去（`pruneFragments`）は無実だった。** 最初にそちらを疑ったが、
`minSize = max(24, largest * 0.04)` は妥当で、複雑度の低下には効いていない。

### 2026-08-11 **測定の注意: run ごとのばらつきが大きい。曲間の比較は同一 run で行うこと**

同じコード・同じ WAV（＝同じ形態シード）で曲を最後まで通しても、
Fury の完成時の複雑度が **10.56 と 7.92** の2つの値を取った（差 26%）。
形成中の値も 11.28 と 12.13 でばらつく（7%）。

原因は特定していないが、**別々の run で撮った数値どうしを直接比べてはいけない。**
比べるなら次のどちらか:

- **同一 run 内の対で見る**（`complete_ab.js` の形成中 → 完成の比のように）
- 同じ条件を複数回測って平均を取る

この注意を立てる前に書いた「曲間の差が 6.25 → 0.05 に潰れた」等の比較は、
別々の run どうしの比較なので**言い切れる精度ではなかった**。方向は合っていても、
数値の細かい差は根拠にしないこと。

### 2026-08-11 「曲の後半は形に残らない」は誤り。**大きさが止まるだけで彫刻は進んでいる**

ユーザー報告「曲中に生成がされなくなる」を段階キャプチャで確かめた
（`song_stages.js`。曲の途中で 3 回＋完成時に撮る）。

Fury Of The Storm（6:47）:

| | 60秒 | 180秒 | 300秒 | 完成 |
|---|---|---|---|---|
| 本体面積 | 29.7% | 29.8% | 29.3% | 23.9% |
| 穴の数 | 9 | 6 | 7 | 5 |
| 複雑度 | 14.07 | 16.86 | 11.72 | 7.92 |

**面積はほぼ一定なのに、穴の数も複雑度も動き続けている。**
充填率の上限（60秒で到達）で止まるのは堆積だけで、彫り込みにはブレーキが掛かっておらず、
後半は彫刻が進んでいる。**したがって「成長を復活させる」方向の修正は的外れ**で、
実際に2回とも失敗した（5章）。

残る問題は「**見た目に動きが伝わらない**」ことで、これはユーザーも問題だと認めている。
大きさを伸ばすのではなく、変化の見せ方で直す（8章）。

比較画像: `docs/volume-progress/volume-stages.png`。

### 2026-08-10 天気・時刻・音楽性の色変化を入れた。**効いたのは色相だけ**

`applyWeatherClayTint` と `evolveSongColors` が空実装で、天気も時刻も曲も
色に反映されていなかった。原則で必須の要素（過去に消して却下されている）なので塞いだ。

変更したのは `src/volume-sculpture.ts` のみ:

- `weatherShift`（`ClayColorShift`）を持ち、`envClayShiftFromWeatherAndHour`
  （**vita と同じ共通関数**）で更新する。基準色相は 0.6。
- 形成中（`updateMaterialLive`）と完成後（`updateAfterlife`）の両方へ効かせる。
  完成後は `applyEnvShiftToSculpturePalette` を通す。
- `evolveSongColors` で 0.5 秒ごとに `deriveSculpturePalette(profile)` を更新し、
  形成中の色を「その曲の色」へ寄せる（hue 0.45 / sat 0.3 / light 0.25 の寄せ幅）。
  毎フレーム導出するほど軽くないので 0.5 秒間隔。色はゆっくり動くので段は出ない。

実測（`docs/aether-progress/tools/weather_color_check.js`。**本体画素のみ**を測る。
背景ドームは天気で派手に変わるので、背景込みで測ると効いていると誤診する）:

| | 実装前 | 実装後 |
|---|---|---|
| 天気による色相の広がり | 0.006 | **0.045** |
| 時刻による色相の広がり | 0.007 | **0.028** |
| 天気による明度の幅 | 0.329 | 0.263 |
| 時刻による明度の幅 | 0.175 | 0.126 |

**明度の差を「効いた」の根拠にしてはいけない。** 実装前から照明側で大きく動いていて、
むしろ実装後のほうが小さい（ずらしの light 成分が照明の変化を一部打ち消すため）。
新規に生まれたのは色相の変化だけ。

切り分け方: `weatherShift` を `createClayColorShift()` に差し替えたビルドで同じ計測をした
（一時的な変更で、計測後に戻してある）。

`npx tsc --noEmit` 通過、`npm run build` 通過、console error 0件。
**ユーザーの実機確認待ち**（天気・時刻で色が動くのが分かるか、動きが小さすぎないか）。

## 5. すでに試して失敗したこと（繰り返さないこと）

- **成長の停止（充填率の上限）を「直そう」とすること。2通り試して2通りとも悪化した。**
  そもそも後半も彫刻は進んでいる（3章）ので、直す場所が違う。
  - **A+B: 上限を 0.10 → 0.25 へ上げ、累積エネルギーで押し上げる**
    → 成長は最後まで続いたが、太ると網目構造が埋まって複雑度が落ちた。
      2曲の複雑度が近づいた（別 run 比較なので数値は参考値）。
  - **C: 堆積を止めず、超過ぶんだけ密度場全体を一様に痩せさせる（質量保存）**
    → **最悪だった。** Fury が穴 5 → 0、複雑度 10.56 → **3.74**（真円が 3.54）で、
      画像でも網目が完全に消えて滑らかな塊になった。
      密度場を一律に縮めても等値面は相似に縮むだけで、
      薄い部分は「割れる」のではなく「均される」。
- **完成時に密度場をぼかす**（`mc.blur`）→ 輪郭の複雑度を最大6割削る（3章）。
  0.25 まで下げても半減する。**戻さないこと。**
- **天気・時刻の色相ずらしに倍率を掛けて強くする。2通り試して2通りとも悪化した。**
  原因は振幅ではなく、完成体が淡すぎて色相が色として読めないこと（3章）。
  - **倍率を上げる**（天気 ×3 / ×5、時刻 ×2.5 / ×5.5）
    → 完成後は `applyEnvShiftToSculpturePalette` のクランプ [0.02, 0.92] に張り付くので、
      **天気の色相幅はむしろ 0.081 → 0.064 に縮んだ。**
  - **ずらしの基準色相を、適用先（完成パレットの 0.1 付近）に合わせる**
    → クランプは解消したが、**全天気が淡い黄緑へ収束して現状より判別できなくなった。**
      さらに倍率を上げると白へ抜ける。比較画像 `../volume-progress/env-weather-gain.png`。
  - 教訓: **明度 0.78 の淡い物体の上では、色相を動かしても色は変わって見えない。**
    次は明度・彩度で伝える。

- **volume を vita の代わりにする** → ユーザーは vita を残すと決めている
  （2026-08-10、「volume を別スタイルとして仕上げる」を選択）。置き換えない。
- **vita の見た目をそのまま移植する** → 別スタイルとして立てる意味が無くなる。
  密度場ならではの見え方を考えること（[../worklist/VOLUME.md](../worklist/VOLUME.md) の [P2]）。
- **背景込みで色の変化を測る** → 背景ドームは天気で派手に変わるので、
  マテリアルが一切変わっていなくても「効いた」ように見える。本体画素だけを測ること。

## 6. 有効だった検証方法

- **曲を通した完成形は headless で作れる。** WAV に変換すればよい（proprietary codec の
  m4a / mp3 だけが再生できない）。`song_run.js` が全自動で
  「再生 → 完成 → 3方向キャプチャ」まで回す。詳細と注意は
  [../aether-progress/tools/README.md](../aether-progress/tools/README.md)。
- 造形の「種類」: `topology.js`（穴の数・破片の数・輪郭の複雑度）。
  **シルエット差の量（xor）では足りない**——床の12〜25倍あってもユーザーは
  「面白くない」と評価した。種類を見ること。
- 天気・時刻の色（数）: `weather_color_check.js`。**待機状態で測っている。**
- 天気・時刻の色（画像）: `env_color_grid.js`。
  **待機で撮ってはいけない**——待機の粒は画面の6%しか無く、並べても色が読めない。
  このスクリプトは曲を60秒聴かせて Complete まで進め、**形が凍った完成後**に環境だけ振る。
  形が全カット共通になるので差は色だけになる。1水準あたり約2分。
  並べるのは `compose.js`。
- **完成処理が何を削っているか: `complete_ab.js`（1回2分）。**
  60秒だけ形成して Complete を押し、**同一 run 内で完成前後を比べる**。
  曲を通すと1回4〜7分かかるうえ run ごとのばらつきに埋もれるので、こちらを使う。
- **曲の後半に何が起きているか: `song_stages.js`。** 曲の途中で段階的にキャプチャする。
- **彫り込みの閃光が出ているか: `flash_check.js`。** 閃光は 0.55 秒で消え、
  彫り込みのクールダウンが 1.6〜2.4 秒あるので**1枚撮っただけでは写らない。**
  連射して白飛び画素の多いコマを残す。「出ていない」と誤診しないため。
- 完成形の比較キャプチャ: dev パネルの「検証用キャプチャ」（向き・画角・解像度を固定）。
- **別々の run の数値を直接比べないこと**（3章の注意）。同一 run 内の対で見る。

## 7. 絶対にやってはいけないこと

- **天気 / 時間 / 音楽性による色変化を消す。** 原則で必須。過去に消して却下されている。
- 明度の変化を根拠に「色が効いている」と報告する（照明側でも動くため）。
- vita を volume で置き換える。
- 上の項目が片付く前に `PUBLIC_EXPERIENCE_IDS` へ追加する（未完成のまま出荷になる）。
